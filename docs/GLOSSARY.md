# Terminology and glossary

This document provides formal definitions for core concepts, terms, and data structures used across Offline Code Context Compiler (OCC).

## Context package
The compiled, structured plain-text document conforming to Wire Format v1, generated by OCC to provide repository context for LLM interfaces. Consists of metadata headers, project structure, architecture overviews, symbol definitions, WHY selection audit records, and fenced source code excerpts.

## WHY entry
A structured audit record associated with each candidate file in a context package. Lists the file's selection tier, composite ranking score, and the specific retrieval signals (such as exact symbol match, direct dependency, or lexical match) that contributed to its inclusion.

## Selection tier
A categorical grouping assigned to candidate files during retrieval:
- Tier 1 (Direct Match): Files containing exact symbol name matches, file name matches, or top-decile lexical hits.
- Tier 2 (Direct Relationship): Direct dependencies (imports), direct dependents (importers), and companion test files.
- Tier 3 (Extended Relationship): Multi-hop dependencies, same-directory neighbors, and call graph neighbors.

## Degradation ladder
The deterministic four-stage fallback sequence applied to candidate files when package token or character budgets are constrained:
1. Full file: Complete file content emitted with line numbers.
2. Symbol blocks: Excerpts restricted to line spans of referenced symbols.
3. Declarations: Interface definitions, type signatures, and function headers without implementation bodies.
4. Metadata only: File path and summary comment retained; source code body omitted.

## Seed
An initial file path, working-tree diff, editor tab, or stack-frame line reference that anchors the retrieval process. Seeds provide starting nodes for relationship graph traversals and inject targeted ranking signals.

## Gold file
In the commit-mined evaluation benchmark, a ground-truth repository file modified by the commit corresponding to the evaluation task.

## Package recall
An evaluation metric defined as the fraction of gold files contained within the finalized context package. Extracted directly from `### FILE:` headings in the `## SOURCE` section of the package output.

## Inverted index
The in-memory lexical data structure mapping tokenized words to files. Supports field-specific weights (symbol 3.0, path 2.0, io 2.0, summary 1.2, identifier 0.8, body 0.5), sublinear term frequency damping (`1 + ln(tf)`), and prefix matching for terms with four or more characters.

## Project fingerprint
A twelve-character hexadecimal digest representing the normalized workspace root path, recorded in `manifest.json`. Used on extension startup to verify that persisted index shards correspond to the current workspace directory.

## SafeGit
The hardened, read-only wrapper around `child_process.execFile` in `src/git/safeGit.ts`. Enforces execution security by passing configuration flags that neutralize repository-level fsmonitor executables, external diff drivers, textconv filters, hooks, and external protocol transports.

## Leak gate
The final, fail-closed security verification pass executed immediately before preview display or clipboard writing. Evaluates the serialized context package text against all detected credential values. If any raw secret string survived redaction, the gate aborts the export with a `SECURITY_BLOCKED` error.

## Sharded store
The on-disk index layout (`src/index/indexStore.ts`) that persists individual file analysis records into separate JSON files (`entries/xx/<hash>.json`). Employs atomic write-to-temporary and rename operations to prevent partial or torn writes upon process termination.
